Auth, RLS & multi-tenancy

Sound

Supabase SSR · variant gate · password reset · RLS isolation

  • Auth: singleton browser client (avoids the pre-hydration RLS write race); server client wraps cookie sets in try/catch; src/proxy.ts runs the variant gate before updateSession. Custom cross-device password-reset is well-designed — 256-bit single-use, race-safe atomic claim, hash-only-in-DB, no enumeration, rate-limited.
  • Variant split: defense-in-depth — build-time branch pruning + proxy redirect/API-404 + login affinity guard + DB trigger guard_jobs_variant(). Three lawn crons intentionally self-gate isLawn() so the construction deploy owns cron against the shared DB (no double-process).
  • RLS: every business table has same_org()/tier_* on every policy + with check on writes; organization_id NOT NULL on 18 tables; BEFORE-INSERT triggers stamp child org from parent even for service-role writes. The 42P17 recursion pattern is consistently fixed via SECURITY DEFINER helpers — no direct cross-table subqueries remain.
  • Service role: used in ~14 routes, always either token-scoped to one org row (public portals) or caller-tenant-scoped via getMyOrg. No cross-org leak path found.

Stripe / payments & the pivot

Pivot cleanly scoped

SaaS subscriptions · Connect "Pay Here" · the QuickBooks question

Two subsystems share one webhook (discriminated by Checkout mode): SaaS subscriptions (your revenue — Stripe Billing, checkout/portal/sync, billing_events, guard_job_create) and Connect "Pay Here" (a contractor's customer pays an invoice via destination charge; webhook marks it paid). The proposed pivot — Stripe keeps only subscriptions; construction receivables move to QuickBooks; lawn BYO Stripe/bookkeeping — is cleanly scoped: Pay Here is a self-contained ~9 files + 1 SQL + 1 webhook branch + 1 env var, with zero coupling into SaaS subs or lawn cycle billing.

✓ SaaS subscriptions are solid and untouched by the pivot

billing.ts (checkout/portal/sync), plans.ts, billing_events, and guard_job_create stay as-is. Subscription status gating (active/past_due/canceled) works server-side and via the DB trigger. Grandfather-on-deploy is one-shot.
